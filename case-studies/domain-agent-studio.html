GoDaddy Airo · 2025

Domain Name Registration Agent

Turning an early business idea into a confident domain choice.

Role
Product Designer
Scope
Agent UX & interaction strategy
Surfaces
Desktop & mobile

I designed how the Domain Agent understands intent, presents recommendations, and guides customers toward registration.

Follow the decisions ↓

The central question

When should an agent keep talking—and when should it give the customer something to act on?

01 / The ecosystem

One front door.
Many specialists.

GoDaddy was evolving Airo into a coordinated system of specialized agents. Airo held the customer context and directed work to the right product expert.

The Domain Agent handled one of those tasks: finding a domain. The experience needed to feel like a continuation of Airo, not a fresh start.

DESIGN INTENT

Carry the customer’s context forward.

System boundary

Airo provides the shared entry point. The Domain Agent brings task-specific guidance. The customer should not have to understand that division to make progress.

02 / Reuse context

Confirm what’s known.
Don’t ask again.

“I want to buy a domain” could mean an existing business or an entirely new venture. The request alone wasn’t enough.

When Airo already knew the customer’s ventures, I surfaced that context as a choice. Confirm an existing business, or start something new.

THE DECISION

Verification before interrogation.

Control, not assumption

Known context is a useful starting point, not a decision made on the customer’s behalf. Keeping “new venture” available prevents personalization from becoming a dead end.

03 / Build intent

Ask for the next signal.
Not the whole brief.

A new business starts with less context. Rather than front-loading a questionnaire, the agent gathers what will improve the next recommendation.

Each response contributes to a visible set of options. Customers can see where the conversation is taking them—and change direction.

THE DECISION

Make progress while learning.

The trade-off

More questions can sharpen relevance, but they also delay the first useful result. The interaction is designed to gather context progressively, alongside recommendations.

04 / Make comparison easier

Talk to refine.
Look to compare.

Chat works well for expressing preferences. It is a poor place to compare a growing list of names, extensions, availability, and prices.

I separated conversation from the results surface. The customer can refine the request without losing the options they are evaluating.

THE DECISION

One continuous task. Two complementary surfaces.

Why a second surface?

The task changes from expressing intent to evaluating alternatives. The interface should change with it; conversation does not need to do every job.

05 / Support the decision

A recommendation.
Then a next step.

Finding an available name is not the end of the journey. Customers still need to understand what they are getting and how to move forward.

The available-domain state brings availability, included value, and the next action together. On mobile, the same decision hierarchy takes priority.

THE DECISION

Keep the value close to the action.

Across screen sizes

The mobile designs preserve the information needed to choose: the recommendation, its value, and a clear next action. Use the Desktop / Mobile control to compare the original designs.

06 / Keep a way forward

The agent can fail.
The journey shouldn’t.

Recovery belongs in the core experience. When the system cannot respond, the interface explains the interruption and keeps retry close at hand.

The same attention extends to waiting, refinement, and the transition toward registration—not just the ideal conversation.

THE DECISION

Make the next move clear, even when the answer isn’t.

Trust in the less ideal moments

A recovery state should acknowledge the problem without requiring the customer to diagnose it. A visible retry gives the conversation a way forward.

07 / Bringing it together

Knowing when
not to chat.

The work defined an interaction model for agent-led decisions: converse while intent is fluid, introduce structure when comparison starts, and make the next action explicit.

The design challenge wasn’t making the agent talk more. It was knowing what the interface should do next.

Shown here: design work and an interaction prototype.

What this case study demonstrates

Context reuse, progressive discovery, coordinated conversation and results, responsive decisions, and recovery. These are design outcomes; no measured business impact is claimed here.
